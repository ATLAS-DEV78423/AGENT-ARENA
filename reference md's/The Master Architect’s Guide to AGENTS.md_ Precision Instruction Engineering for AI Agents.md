### The Master Architect’s Guide to AGENTS.md: Precision Instruction Engineering for AI Agents \#\#\#\# 1\. The Strategic Shift: Transitioning from Documentation to Instruction We are entering a phase of autonomous development where the primary consumer of repository context is no longer exclusively human. This necessitates a strategic shift from human-centric READMEs to machine-actionable AGENTS.md files. While traditional documentation focuses on project rationales and historical context to build developer intuition, an AGENTS.md functions as a "README for Agents"—a dedicated, predictable context store designed to eliminate "cold starts" and state drift in AI interactions. By providing a standardized entry point for context, we transform a repository from a collection of files into an agent-ready environment. The critical differentiator lies in the payload: human documentation explains rationales; agent instructions mandate execution boundaries. Where a human can infer meaning from project history, an agent requires exact versions, specific execution flags, and rigid constraints. This distinction is the definitive defense against "AI Slop"—the generic, verbose, or hallucinated outputs that occur when a model is forced to guess at an undocumented convention. Precise instruction engineering ensures the agent moves past "guessing" and into high-fidelity "execution." Establishing this foundational structure is the first step toward transforming your repository into an infrastructure for agency. \#\#\#\# 2\. The Essential Architecture: File Structure and Hierarchy A predictable, standardized file structure is the baseline requirement for reducing agent friction. If an agent exhausts its "attention budget" navigating the directory tree to discover a build command, its performance on complex logic will degrade. Standardizing the location of context allows the model to orient itself instantly upon session start. \#\#\#\#\# The Six Mandatory Sections Industry analysis of over 2,500 successful repositories identifies six critical sections that should comprise every AGENTS.md: 1\. **Project Stack:** Specify exact versions (e.g., TypeScript 5.4, React 19, Bun runtime). Specificity prevents the use of deprecated APIs. 2\. **Build and Test Commands:** Provide exact executable commands with required flags (e.g., bun run lint \--fix). 3\. **Code Style Conventions:** Define language-specific patterns (e.g., "Always use functional components with hooks; never use class components"). 4\. **Architecture Constraints:** Provide a directory map and module boundaries (e.g., "Never import from /app into /lib"). 5\. **Boundaries:** Define explicit "Never Touch" zones, such as /generated/ folders, legacy modules, and a hard prohibition against committing secrets. 6\. **Git/Workflow:** Mandate branch naming, PR conventions (e.g., "Squash merge only"), and commit message formats (e.g., Conventional Commits). \#\#\#\#\# Monorepo Implementation and Nested Logic For large monorepos, the architecture relies on a "closest file wins" logic. A root-level AGENTS.md defines global defaults, while nested AGENTS.md files in subprojects provide specialized overrides. When an agent acts within a subdirectory, it walks up the directory tree to concatenate instructions. The file closest to the active working directory takes precedence, ensuring a Python agent in the backend doesn't attempt to apply React conventions found in the project root. Once the structural hierarchy is established, success depends on the nuances of phrasing and linguistic precision. \#\#\#\# 3\. Phrasing Styles: The "Show, Don't Tell" Methodology Phrasing directly impacts an agent's attention budget and rule adherence. Descriptions often get diluted in the context window; strong, instructive examples provide immediate grounding. \#\#\#\#\# Descriptive vs. Instructive Phrasing | Descriptive/Weak Phrasing (Avoid) | Instructive/Strong Phrasing (Prioritize) | | \------ | \------ | | "We generally prefer modern React patterns like functional components." | " **CORRECT:** export const User \= () \=\> { ... }

**WRONG:** class User extends React.Component { ... }" | | "Please ensure that you handle errors using our global handler." | "Let errors propagate. Do not wrap in try/catch. The global handler in middleware.ts catches everything." | \#\#\#\#\# The "Senior Dev Ladder" and Root-Cause Philosophy To prioritize efficient code over clever abstractions, instruct agents to climb the "Senior Dev Ladder." Before writing a single line, the agent must evaluate: 1\. **YAGNI:** Does this need to be built? 2\. **Reuse:** Does a helper or pattern already exist in the codebase? 3\. **Standard Library:** Does the native language solve this? 4\. **Native Platform:** Does the platform feature cover it? 5\. **Dependencies:** Does an installed library solve it? 6\. **One-liner:** Can this be a single line? 7\. **Minimum Code:** Only then, write the minimum functional diff. Crucially, an architect’s agent must understand that **Bug Fix \= Root Cause, not Symptom.** If a ticket identifies a symptom, the agent must grep every caller of the affected function and fix the shared logic once. A single guard in the source is a smaller, safer diff than patching every individual caller. \#\#\#\#\# The Glossary Technique Define specific entities to ensure clear ownership and perspective. Use a Glossary section to define: \* **"You":** The AI agent reading the file. \* **"We" / "Maintainers":** The human developers (e.g., "Theo and the maintainers"). \* **"User":** The person directing the agent. \* **"Environment":** The machine, file system, and state owned by the runner. Defining these roles prevents the agent from confusing its identity with the maintainer's intent, leading to more professional and aligned contributions. This clarity transitions naturally into the technical annotation of priority. \#\#\#\# 4\. Annotation and Priority Signage: Visual Cues for Machines Agents require structured visual cues to distinguish between suggestions and hard constraints. Without priority markers, the model may treat a style preference with the same weight as a security boundary. \#\#\#\#\# Priority Signs and Formatting \* **XML Tags:** Wrap content in , , and tags. This helps modern models parse complex prompts and prioritize content wrapped in specific markers. \* **The "Ponytail" Comment:** Use named comments (e.g., // ponytail: ceiling) to mark deliberate simplifications. This signals to the agent that a technical ceiling (like an O(n²) scan) was chosen for efficiency, and it defines the intended upgrade path. \* **The "Correct vs. Wrong" Block:** Code blocks labeled // CORRECT and // WRONG provide high-contrast examples that are more effective than paragraphs of prose. \* **Specific Identifiers:** Use Markdown H2 and H3 headers to denote logical tool/command groups, making the file easily navigable for the agent's internal parser. \#\#\#\#\# Grounding Quotes In long-context scenarios, require the agent to use "Grounding Quotes." Instruct the agent to quote the relevant section of the AGENTS.md before performing a task. In complex, multi-document inputs, grounding quotes improve response quality by up to 30% by forcing the model's attention onto the source document before it acts. These signs provide the "runtime" guidance, transitioning to the "Compounding Engineering" workflow that captures history. \#\#\#\# 5\. Compounding Engineering: The MISTAKES.md and Graduation Workflow Compounding Engineering is the process where agents learn from history to stop repeating mistakes. Rather than "cold starting" every session, we use a structured loop to build institutional knowledge. \#\#\#\#\# The Lifecycle of a Rule 1\. **Mistake Logging:** When an agent fails or is corrected, it appends the error to a MISTAKES.md file. The entry must include: what happened, the root cause, and the prevention strategy. 2\. **Pattern Recognition:** The log serves as an "evidence store." It is not for runtime lookup but for identifying recurring failures. 3\. **Rule Graduation:** Once a failure shows up four or five times, it "graduates" from the log into a one-line "hard law" within the main AGENTS.md. \#\#\#\#\# The "Deposit-then-Audit" Split To keep the always-on context small and effective, implement a "Deposit-then-Audit" split: agents are authorized to log data (deposit), but a human maintainer (or an auditor agent) must approve the graduation of rules. This prevents the AGENTS.md from becoming a verbose diary of one-off errors and keeps the core instructions focused on high-frequency patterns. As these rules graduate, they must adhere to strict technical constraints to ensure optimal performance. \#\#\#\# 6\. Technical Optimization and Perfect Export Formatting Instruction files have technical ceilings. A file that is too large consumes the context window, increases latency, and degrades adherence to core rules. \#\#\#\#\# Critical Technical Constraints | Metric | Requirement | | \------ | \------ | | **Line Limit** | Aim for \<150 lines. Files \>150 lines increase inference costs 20-23% without improving performance. | | **Token Budget** | Limit to 32 KiB to avoid truncation by loaders like Codex. | | **Formatting (PDF)** | Use standard Markdown. No Mermaid or code execution blocks. Use clear H1/H2 hierarchies for high-fidelity PDF rendering. | \#\#\#\#\# The Claude Code Exception and Consolidation Consolidate project-specific logic into a single AGENTS.md. However, a critical technical friction exists: **Claude Code reads** **CLAUDE.md** **, not** **AGENTS.md** **.** To maintain a universal truth while supporting all tools, you must use one of two strategies: 1\. **The Import:** Create a stub CLAUDE.md containing only @AGENTS.md. Claude Code will load the imported file at session start. 2\. **The Symlink:** Use ln \-s AGENTS.md CLAUDE.md. (Note: This requires Developer Mode on Windows). This ensures you avoid "instruction drift" where different tools operate under different versions of the rules. With the technical infrastructure set, we move to the final summary of prohibited and prioritized behaviors. \#\#\#\# 7\. The Definitive Directive: Proactive Do’s and Don’ts Strict adherence to these mandates prevents the "AI Slop" aesthetic and ensures your agent operates as a high-functioning technical peer. \#\#\#\#\# Final Mandates \* **DO:** Hand-write the initial file; LLM-generated drafts lead to generic, verbose advice that increases task steps by up to 3.92%. \* **DO:** Include directory maps and provide 3–5 diverse code examples. \* **DO:** Version control the AGENTS.md to track the evolution of your instructions. \* **DON'T:** Include secrets, API keys, or credentials. \* **DON'T:** Use passive voice or vague requests like "Follow best practices." \* **DON'T:** Over-engineer with unnecessary abstractions or hypothetical future requirements. **Instruction engineering is not documentation; it is the infrastructure for autonomous agency.** By treating your AGENTS.md as a living, precision-engineered component of your codebase, you move from reactive debugging to proactive, compounding productivity.
